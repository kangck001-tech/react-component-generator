# commit: 변경사항 분석 후 컨벤션 커밋

작업 디렉토리의 변경사항을 분석해 논리적 단위로 나누고, 한국어 커밋 메시지를 만들어 **승인 절차 없이 바로** 커밋한다. 커밋 결과는 마지막에 보고한다.

## 커밋 메시지 컨벤션

형식: `타입: 요약`

| 타입 | 용도 |
|------|------|
| `feat` | 새 기능, 화면, 동작 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `chore` | 설정, 의존성, 빌드, 문서 등 기타 |

- 요약은 한국어로 쓰고 50자 안팎, 마침표 없이 "~추가", "~수정", "~개선"처럼 명사형으로 끝낸다.
- 요약은 무엇이 바뀌었는지가 아니라 **왜/무엇을 위해** 바뀌었는지가 드러나게 쓴다.
- 필요하면 빈 줄 뒤에 본문을 붙여 이유와 영향 범위를 적는다. 본문도 한국어로 쓴다.
- 위 4개로 설명되지 않는 경우(`test`, `docs`, `style` 등)는 저장소의 기존 커밋 로그 관례를 따른다.

## 절차

### Step 0: 저장소 확인

1. `git rev-parse --is-inside-work-tree`로 git 저장소인지 확인한다. 아니면 중단하고 "git 저장소가 아닙니다. `git init`이 필요합니다."라고 알린다. 임의로 `git init`을 실행하지 않는다.
2. 저장소 루트의 `AGENTS.md`/`CLAUDE.md`에 커밋 지침이 있으면 이 스킬의 컨벤션보다 우선한다.
3. `git log --oneline -10`으로 기존 메시지 스타일을 확인해 톤을 맞춘다.
4. 현재 브랜치가 기본 브랜치(`main`/`master`)이면 새 브랜치를 만들어 거기에 커밋하고, 그 사실을 결과 보고에 적는다.

### Step 1: 변경사항 분석

1. `git status --short`로 변경 파일 목록을 본다. 스테이징된 것, 안 된 것, untracked를 구분한다.
2. `git diff`(unstaged)와 `git diff --staged`(staged)로 실제 내용을 읽는다. untracked 파일은 내용을 직접 읽어 성격을 파악한다.
3. 변경이 없으면 "커밋할 변경사항이 없습니다."라고 알리고 끝낸다.
4. 다음 파일은 커밋 대상에서 제외하고 사용자에게 알린다.
   - `.env`, 키·토큰·인증서 등 비밀 정보가 담긴 파일
   - `node_modules`, `dist`, 로그, 임시 파일 등 `.gitignore` 대상이어야 할 산출물
   - 변경 내용에 비밀 값이 하드코딩된 경우도 해당 줄을 짚어 알린다.

### Step 2: 논리적 단위로 분류

1. 변경을 **목적이 같은 것끼리** 묶는다. 한 커밋은 한 가지 이유로 설명되어야 한다.
   - 기능 추가와 그에 딸린 테스트는 같은 커밋에 둔다.
   - 리팩터링과 기능 변경이 섞여 있으면 분리한다.
   - 포매팅, 의존성 업데이트, 설정 변경은 별도 커밋으로 뺀다.
2. 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 hunk 단위 분리(`git add -p`는 대화형이라 쓸 수 없으므로 `git apply --cached`로 패치를 적용)가 가능한지 판단하고, 어렵다면 한 커밋으로 묶되 그 사실을 알린다.
3. 변경이 작고 목적이 하나면 커밋 1개로 충분하다. 억지로 쪼개지 않는다.

### Step 3: 커밋 메시지 작성

각 단위마다 타입을 고르고 한국어 메시지를 쓴다. 타입이 애매하면 사용자 관점의 효과를 기준으로 고른다. 예를 들어 화면이 바뀌었으면 `feat`, 동작이 깨진 걸 고쳤으면 `fix`, 겉모습은 그대로 두고 코드만 정리했으면 `refactor`다.

커밋 메시지 끝에 현재 세션의 시스템 지침이 요구하는 Co-Authored-By 같은 attribution 줄이 있으면 그대로 붙인다. 지침이 없으면 붙이지 않는다.

### Step 4: 커밋 계획 안내 (승인 불필요)

커밋하기 전에 아래 형식으로 계획을 간단히 출력한다. 승인을 기다리지 않고 바로 Step 5로 넘어간다.

```
커밋 계획 (총 N개)

1. feat: 레트로 데스크톱 테마로 전체 화면 개선
   - src/App.tsx
   - src/App.css
   - src/index.css

2. chore: 한글 픽셀 서체 CDN 추가
   - index.html

제외한 파일: .env (비밀 정보)
```

- 사용자가 커밋을 요청한 것 자체가 실행 허가다. 별도로 묻지 않는다.
- 잘못 커밋했다면 사용자가 요청할 때 새 커밋으로 바로잡는다.

### Step 5: 커밋 실행

1. 단위별로 **파일을 명시해서** 스테이징한다. `git add -A`, `git add .`는 쓰지 않는다.
2. 메시지가 여러 줄이면 heredoc으로 `git commit -F -`에 전달한다.
3. 훅(pre-commit 등)이 실패하면 `--no-verify`로 우회하지 않는다. 원인을 설명하고 고친 뒤 **새 커밋**으로 다시 시도한다. 이전 커밋을 `--amend`하지 않는다.
4. 모든 커밋이 끝나면 `git log --oneline -N`과 `git status --short`로 결과를 보여준다. 남은 변경이 있으면 그 이유를 설명한다.

## 하지 않는 것

- push, force push, rebase, reset 등 히스토리나 원격에 영향을 주는 명령은 사용자가 따로 요청하지 않는 한 실행하지 않는다.
- 비밀 정보 파일(`.env` 등)은 승인 절차가 없더라도 절대 커밋하지 않는다.
- 영어 메시지를 쓰지 않는다. 타입 접두어(`feat` 등)와 코드 식별자만 원문을 유지한다.
