# TDD 규칙

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 예외 판단이 필요해 보여도 아래 기준을 임의로 완화하지 않는다. 적용 여부가 애매하면 TDD를 적용한다.

## 0. 프로젝트별 규칙 우선 조항

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 있으면 **그 규칙을 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 상위 문서에 해당 내용이 없을 때만 적용한다.

## 1. 적용 기준

### TDD를 **반드시 적용**하는 대상

- **비즈니스 로직**: 계산, 검증, 상태 전이, 권한 판단
- **API**: 엔드포인트, 요청/응답 처리, 미들웨어
- **유틸 함수**: 순수 함수, 변환, 포맷터, 파서
- **버그 수정**: 재현 테스트를 먼저 작성한 뒤 수정한다

### TDD가 **불필요한** 대상

- **타입 정의**: 타입/인터페이스만 있는 파일
- **설정 파일**: 빌드, 린트, 환경 설정
- **순수 UI**: 스타일, 마크업 구조만 있는 컴포넌트 (동작 로직이 있으면 로직 부분에 TDD 적용)
- **SQL**: 스키마/마이그레이션 (쿼리가 포함된 로직은 해당 로직을 TDD로 작성)

## 2. RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트**로 작성한다.
- 작성 후 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유는 **"기능 미구현"** 이어야 한다.
  - 허용: `함수가 정의되지 않음`, `기대값과 반환값 불일치`
  - 불허: 문법 오류, 잘못된 import 경로, 설정 오류로 인한 실패

### GREEN: 최소 코드로 통과

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 현재 테스트가 요구하지 않는 기능, 분기, 일반화를 추가하지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 확인한다.

### REFACTOR: 구조 개선

- 중복 제거, 이름 개선, 헬퍼 추출을 수행한다.
- 모든 테스트가 **green을 유지**해야 한다.
- **새로운 동작을 추가하지 않는다.** 새 동작이 필요하면 RED로 돌아간다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.**
- 한 사이클은 짧게 유지한다. 한 번에 여러 동작을 구현하지 않는다.

## 3. 삭제 강제 규칙

- **테스트 전에 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작한다.**
- 삭제한 코드를 **"참고용"으로 남기는 것은 금지**한다.
- 기존 코드에 테스트를 나중에 추가하는 경우도 동일하다. 동작을 검증하는 실패 테스트를 먼저 작성하고, 필요한 경우에만 코드를 다시 작성한다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트가 불필요하다" | **단순한 코드일수록 테스트는 몇 초면 끝난다.** 단순하다는 판단 자체가 검증되지 않은 가정이다. |
| "나중에 테스트를 추가하겠다" | **나중에 쓴 테스트는 구현에 맞춰져서 동작을 검증하지 못한다.** 실패를 본 적이 없는 테스트는 신뢰할 수 없다. |
| "시간이 없다" | **디버깅과 회귀 수정에 드는 시간이 테스트 작성 시간보다 항상 길다.** 시간 부족은 테스트를 생략할 근거가 아니라 범위를 줄일 근거다. |
| "삭제하면 낭비다" | **잘못된 순서로 작성된 코드는 이미 비용이 발생한 상태다.** 검증되지 않은 코드를 남기는 것이 더 큰 낭비다. |
| "프로토타입이다" | **프로토타입도 결국 프로덕션으로 넘어온다.** 프로토타입은 TDD를 면제받는 이유가 되지 않는다. |

## 5. 완료 전 체크리스트

- [ ] 모든 새 동작에 대응하는 테스트가 있다.
- [ ] 각 테스트가 **실패하는 것을 실행으로 확인**했다.
- [ ] 실패 이유가 **기능 미구현**이었다.
- [ ] 프로덕션 코드는 **테스트를 통과시키는 최소 코드**다.
- [ ] 전체 테스트가 **green**이다.
